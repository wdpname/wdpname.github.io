自定义RPC的个人理解

发表于2024-06-13|更新于2024-09-22
|阅读量:

简易版整体流程

消费者调用rpc，触发动态代理（ServiceProxy），在代理中对请求参数处理赋值及代替消费者发送请求到服务提供者。发送请求后（其中会对请求对象进行序列化），来到了rpc模块下的请求处理器。（反着来，把拿到的字节数组反序列化为请求对象）。从拿到的请求对象的相关属性从本地服务注册地di 拿到真正要调用的服务（通过反射调用方法）。拿到结果后将结果设置到响应中。在消费者拿到响应的body数据，反序列化为响应对象返回给消费者。rpc调用完毕。

为什么要用rpc，而不是用http请求呢

需要启动etcd服务器

一个模块 代表一个 依赖，可以被其他模块引入

（重要）简易版：

1. 消费者通过JDK动态代理服务接口发送请求，转而执行invoke方法，在里面首先实例化一个jdk序列化器。随之构造一个自定义Request对象，用拿到的参数设置到request对象中。并序列化request对象，通过hutool发送http请求，其中请求体是原来的序列化request对象的字节数组。
1. 提供者的请求处理器拿到这个请求。从body中获取字节数组，反序列化为自定义request对象。从其中的对象拿到相应的参数信息。从而利用反射调用服务方法。获取的结果设置到自定义response对象中。最后将response对象返回给消费者
  • 实现自定义协议

首先自定义协议如何在网络中传输，参考http协议，我们使用tcp传输层协议，更加轻量。请求头没有那么多信息。请求头包含常有得魔数啊，协议版本号，序列化器标志啥的。

然后是如何定义网络消息结构。消息头，消息体。消息头中包含一些元信息。

spi + 工厂的方式 給系统加功能。比如负载均衡，重试机制，序列化器不同的选择。

提高系统可靠性的两种方式

  1. 重试机制
  2. 容错机制

这两个 加上 之前负载均衡都是相对于消费者这端的。

实现自定义协议

这里我们从http协议换成了tcp协议，但是tcp协议传输的是buffer，这个类型不能传输请求和响应对象，所以这里需要加编码器和解码器。并且在编码器和解码器指定消息头和消息体的位置和大小，这样就不需要额外记录信息，提高效率，缩小传输体积。

构造sdk 编写spring.factories文件，内容是一个配置类，加上@ConfigurationProperties注解。

面试 对策

  1. 熟悉Java核心技术：
    1. 在项目中，我通过选择合适的集合类来优化性能。例如，针对高并发场景中的大数据处理，我会根据数据访问的频率选择 HashMap 来提升查找效率，并且通过设置合适的初始容量，减少了扩容的开销。此外，对于需要有序的数据，我选择了 LinkedHashMap 来保证插入顺序，同时提高了内存利用率。
    2. 在处理大文件或高并发网络请求时，我通过使用 BufferedInputStream 和 BufferedOutputStream 减少了每次读取或写入的系统调用次数，显著提高了 IO 操作的效率。此外，我还将 NIO 引入到项目中，通过 Channels 和 Selectors 来管理多路复用，成功提升了网络请求的吞吐量，尤其是在高并发场景下。
    3. 在项目中，我发现 Java 默认的序列化在传输大量对象时性能瓶颈明显。我优化了这一点，通过使用 Protocol Buffers 来替代 Java 自带的序列化机制，减少了序列化数据的大小和时间。此外，我还通过使用 transient 关键字，避免了不必要的字段序列化，有效降低了内存和存储的开销。
    4. 在某些项目中，我们使用了反射来进行动态方法调用和对象创建，但反射开销较大。为此，我通过缓存 Method 和 Constructor 的反射结果，减少了重复获取的性能损耗。此外，我在性能关键路径中避免了不必要的反射调用，将静态调用替代反射调用，成功降低了执行时间。
    5. 在项目中，我通过选择适合的动态代理机制来优化性能。比如，JDK 动态代理只能代理接口，而在某些类的代理需求中，我使用了 CGLIB 来生成代理类，性能更好。此外，我通过简化代理链，减少代理层的嵌套次数，使得系统整体性能得到了提升。

关于mysql

  1. 表操作 是如何操作的 目标：整理出一个完整文档在表的结构设计中，
    1. 通常我会选用varchar，而不是text，这样有助于节省存储在一些高频查询的场景，我会为表增加一些冗余字段来减少联表查询，提高查询效率此外我会为关键字段设置主键和外键约束，来保证数据的完整性和一致性。
  2. 查询优化 是如何做的
    1. 通过查看mysql的慢查询日志，找到慢查询sql
    2. 通过分析，调整索引以及修改查询语句来优化
    3. 比如 为常用的查询条件列设置索引，为多个字段设置联合索引
    4. 在查询语句的编写中，我会避免使用select *，只选择需要的字段
    5. 当数据表较大时，我通过使用mysql的分区表功能，将数据按照日期进行分区，以此来提高查询速度
    6. 在一些高并发场景中，为减轻mysql的压力，引入redis缓存机制，避免频繁的数据库读取操作。同时使用redis的分布式锁，确保多个线程并发访问相同数据时，避免出现死锁和锁等待的问题。
  3. 索引设计
  4. 事务管理
    1. 事务的四大特性 原子性 一致性 隔离性 持久性
    2. 通过锁机制和mvcc来管理并发事务。在innodb引擎中，通过使用行锁而不是表锁来支持高并发事务。
    3. mvcc使用隐藏列和版本号来管理事务的可见性。
    4. 为了较少锁冲突，使用精细度更小的行锁，以及避免长事务
  5. 隔离级别
    1. 读未提交
    2. 读已提交
    3. 可重复读
    4. 串行化
  6. 高并发场景下的数据库优化
    1. 通过使用redis的缓存机制，减轻数据库的压力
    2. 使用合适的索引，避免全表扫描；对查询sql进行优化。
    3. 根据不同的业务场景，选用不同的隔离级别。比如读多写少的场景，可以实现读已提交隔离级别；而对于一些关键的交易场景，可以实现可串行化隔离级别，来来保证数据的绝对一致性。
    4. 同样可以选择将一些常查询的表且数据量大时，将表分区或者分库分表，以此来提高系统的并发性能。
    5. 避免长事务
    6. 合理调整数据库连接池参数

关于redis

  1. redis数据类型
    1. string：用来存储字符串和数字，适合使用场景例如用来做计数器，常用命令set，get
    2. hash：用来存储对象，例如用来存储用户信息，常用命令有 hset hget
    3. list：支持链表操作，用于实现队列，栈等，例如社交网络的最新动态。常用命令lpush，lpop，rpush，rpop
    4. set：表示无序不可重复集合，支持快速的集合运算。例如共同好友推荐。常用命令sadd，srem
    5. zset：与set类似，每个元素关联一个分数，可通过分数排序。例如游戏中的积分排行榜。常用命令zadd，zrem
  2. 持久化
    1. Redis 提供两种主要的持久化方式：RDB 和 AOF。RDB 是通过生成全量快照来保存数据，适合定期备份，缺点是无法实时保存数据，可能会有数据丢失。AOF 则通过将每次写操作记录到日志中，具备更强的实时性，但日志文件较大，重启时恢复数据速度慢。
    2. 在实际项目中，如果对数据丢失比较敏感，我会选择 AOF，并且设置 appendfsync everysec 以保证数据的实时性。而对于备份需求，我会结合 RDB 进行定期快照。同时，我会定期执行 AOF 日志重写来减少文件体积。此外，使用 Redis 4.0 引入的混合持久化，可以在性能和数据安全之间取得更好的平衡。
    3. 为了优化 Redis 的持久化性能，我会将持久化操作异步执行，确保不会阻塞主线程。同时，通过合理配置快照频率和使用 SSD 提升磁盘 I/O 性能，确保系统在高并发场景下的稳定性。
  3. 淘汰策略
    1. Redis 提供了多种淘汰策略来应对内存不足的情况，主要有 LRU（最近最少使用）和 随机淘汰 两类，以及 TTL（最近即将过期）和 无淘汰 的策略。在实际项目中，我通常会根据业务需求选择不同的策略。
    2. 例如，对于缓存系统来说，我会选择 allkeys-lru 策略，这样可以优先淘汰不常用的数据，确保内存中存储的都是热点数据，提升缓存命中率。如果是会话管理系统，可能会选择 volatile-lru，仅从过期键中淘汰最近最少使用的键，以避免影响到重要的持久数据。
    3. 同时，我们在生产环境中会定期监控 Redis 的内存使用情况，通过调整 maxmemory 参数和淘汰策略，确保系统稳定运行。在高并发场景下，我也会评估是否需要启用 noeviction 策略，以确保业务的关键数据不被意外淘汰。
  4. 高并发缓存处理经验
    1. 在高并发场景下，缓存处理主要面临缓存穿透、雪崩、击穿以及缓存与数据库不一致的问题。为了应对这些挑战，我在项目中采取了以下措施：
    2. 缓存穿透：我通过引入布隆过滤器，拦截不存在的数据请求，防止无效请求直接打到数据库。同时，对查询结果为 null 的数据进行缓存，避免重复请求查询数据库。
    3. 缓存雪崩：为避免大规模缓存同时失效引发雪崩，我在设置缓存时引入了过期时间的随机化，使缓存失效时间分散。此外，结合限流和熔断机制，避免瞬时高并发对数据库造成冲击。
    4. 缓存击穿：对于热点数据，我使用了分布式锁确保只有一个线程能重建缓存，其他线程等待或返回旧缓存。同时，为了避免热点数据失效带来的性能问题，我还设置了定期预加载缓存的机制，确保热点数据始终在缓存中有效。
    5. 缓存与数据库不一致： 在高并发更新场景中，我采用了延迟双删策略，在更新数据库后，先删除缓存，再延迟删除，确保缓存和数据库数据一致性，避免了频繁更新时缓存不一致的问题。
